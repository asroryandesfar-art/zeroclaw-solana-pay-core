# Payment verification

`create-url` first validates locked merchant, asset, amount, reference, cluster, and expiry, then persists the invoice before returning `registered=true`. `settle` loads those persisted terms; caller supplied amount or merchant fields cannot change them. On Mainnet it requires finalized RPC evidence. Only `newly_settled=true` represents a new atomic `pending → paid` claim.

For both assets the verifier requires a matching fetched signature, successful transaction, sufficient commitment, invoice block time from issue through expiry, correct genesis hash, and a compiled transfer instruction with the invoice reference among that instruction's extra accounts. It checks the recipient's positive balance change and caps credited value by the amount of the proven transfers. A reference elsewhere in the transaction, a string match, screenshot, or payer message cannot settle an invoice.

SOL requires a System Program transfer to the merchant wallet and a matching lamport increase. USDC requires a legacy SPL Token Program transfer to the merchant's associated token account, the canonical cluster mint, token balance metadata naming the merchant owner and Token Program, six decimals, and sufficient base units. Mainnet queries the canonical mint account at finalized commitment. Token symbols and metadata supplied by the payer are ignored. The verifier parses top level and inner compiled instructions, including address lookup table accounts. Other instruction programs cannot impersonate a transfer. See [Solana token transfer](https://solana.com/docs/tokens/basics/transfer-tokens) and [token accounts](https://solana.com/docs/tokens/basics/create-token-account).

SQLite holds unique invoice references, unique `(cluster, recipient, order_id)` when an order ID exists, and globally unique settled signatures. An issue or paid transition atomically appends a local audit event without customer identity or credentials. A transactionally claimed signature cannot pay another invoice. Repeated settlement reports `newly_settled=false`. The finite signature scan can miss older payments; an absent result means pending, not proof that no transfer happened. A late, underpaid, or reference-free payment must be recorded for operator reconciliation rather than automatically fulfilled or discarded.

The CLI trusts the configured RPC provider's chain view after genesis and response checks. It does not independently verify blocks or validator votes. There is no automatic refund or payer private key handling.
